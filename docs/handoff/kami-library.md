# Kami concept library
Summary: hand-written answers to concept questions ("what is miai?") in `src/lib/coach/library/`, with example positions whose every claim and number comes from KataGo reads.

## Layout
- `concepts/*.ts`: the texts, by theme (basics, tactics, shape, tempo, strategy, opening, endgame). Each entry: id, name, aliases (English, romaji, kana/kanji, Chinese, Korean), level, one-sentence `short`, 3 to 5 body sections, mistakes, related ids.
- `examples.ts`: generated by `scripts/concept-examples.ts`, never edited by hand. Compact records (stones as SGF coordinates); `index.ts` decodes them into `ConceptExample`s.
- `index.ts`: `CONCEPTS`, `findConcepts`, `conceptById` (contract names), plus `scoreConcepts`, `normalizeQuestion`, `decodeExample`. Types live in `types.ts` and are re-exported.
- Contract change (backwards compatible): `ConceptExample.view?: [x0, y0, x1, y1]`, the part of the board to show. Framed examples fill the rest of the board with settled stones, so a viewer should zoom to `view`.

## Counts (this PR)
- 45 concepts; all 14 `ConceptId`s from `explain/types.ts` have an entry with the same meaning.
- EXAMPLES_LINE
- Bundle: about 120 KB minified, 39 KB gzipped for the whole library. Kami can lazy-load it.

## Add a concept
1. Add an entry to the matching `concepts/*.ts` file; ids are kebab-case, `related` must point at existing ids.
2. Aliases must be unique across the library (a test checks). Avoid single CJK characters and everyday English words where a longer term exists; if you must add a common word, also add it to `WEAK` in `index.ts` so it only counts in a Go question.
3. Write accurately and plainly: rules and proverbs you are sure of, no engine numbers in the text (numbers belong in examples, from reads).
4. `npx vitest run tests/concept-library.test.ts`.

## Add an example
1. Add a spec at the bottom of `scripts/concept-examples.ts`: a framed local diagram (`local`, rows of X/O/. in a corner; the attacker's frame surrounds it, komi `'even'`), stones on an open board (`black`/`white`), or a real position (`bank: '<problem id>'`).
2. Give checks; the note may only use `{placeholders}` the checks fill (`{m1}`... are the line's moves, so coordinates are never typed by hand). Check kinds: `top`, `beats`, `loses`, `owns`, `reply`, `tenuki`, `local`, `swing`, `costs`, `captures`, `illegal`.
3. Run `npx tsx scripts/concept-examples.ts --inspect --only <concept>` (prints KataGo's top moves and the captures along the line; writes nothing). Add `--merge` to replace just those concepts' examples in `examples.ts`; a run without `--only` rewrites the whole file (about 25 minutes at 800 visits). Failed checks are dropped and printed, never kept with a softer note.

## Gotchas
- Engine bug (not fixed here, not my file): `searchProber` feeds setup stones through `engineMoves` (all Black stones, then all White ones), and the engine misreads that: the same 8 stones read B+55.6 instead of B+26.7, framed problems read B+80..96 at any komi with pass on top. The script works around it (`alternating()`: setup as alternating moves with passes). Positions stored in `examples.ts` keep normal setup stones, so Kami's own reads of them are wrong until `engineMoves` interleaves colours.
- Ownership of a stone that can be laddered or netted stays well below 1 until it is captured (the aji of a later breaker), so example claims use the played-out line, not the ownership right after the first atari.
- The b10 net at 800 visits sometimes disagrees with the problem bank's answer (built natively); those examples are dropped, not forced.
- Swing values compare "mover plays X, opponent passes" with "mover passes, opponent plays X", both with the mover to play, so the tempo cancels and the number is the deiri value.
- `tenuki` compares KataGo's best answer with its best move at least 4 lines away (a pass in framed positions).
