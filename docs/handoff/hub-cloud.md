# Dop hub: setup

You type a task on one page, from your phone or computer. A Claude coordinator splits it into threads and hands them to your Claude accounts. Paid accounts do the coding; free accounts help with questions, research and writing.

## Part 1: make the hub (once, about 5 minutes)
1. Sign in to **vercel.com** (a new account is fine). Click **Add New** › **Project**. If Vercel asks, connect GitHub and allow it to see the **Dop** repo. Pick **Dop**.
2. Name it `dop-hub`. Next to **Root Directory**, click **Edit** and pick `hub`.
3. Open **Environment Variables** and add one: name `HUB_PASSWORD`, value any password you like.
4. Click **Deploy**.
5. In the new project, open **Storage** › **Create** › **Upstash Redis** (free plan) › connect it to `dop-hub`. Then open **Deployments**, click the **⋯** on the top one, and choose **Redeploy**.

Now open the hub's link and type your password. On your phone, use "Add to Home Screen".

## Part 2: add a paid account (Pro or Max)
1. On the hub page: **Add account**, type a name (like *Main*), choose the plan, **Save**.
2. Press **Connect** on that account and copy the link.
3. On claude.ai, signed in as that account: **Settings** › **Connectors** › **Add custom connector**. Name it *Dop hub*, paste the link, tick **No sign-in** (claude.ai marks it Detected; leave any OAuth client choice alone) and press **Add**; if a **Connect** button appears, press it (no sign-in page should open). **Test link** on the Connect screen checks the link first; **New link** makes a fresh one (connectors and routines using the old link stop working until you add the new one). Add stays grey while "Sign in now" with "Use your own OAuth client" is picked (it wants a client ID), until Name and URL both have text, or if that account already has a connector with the same link (**New link** fixes that). Use the link from the hub's main address (Vercel › Domains); single-deployment links are locked behind a Vercel login and fail with a sign-in error.
4. On claude.ai/code: **Routines** › **New routine**. Pick the Dop repo and a model, turn on the Dop hub connector, add an **API trigger**, and paste the prompt from the Connect screen. Copy the routine's id and token into the hub (**Edit** on that account). Repeat for each model you want on that account.

## Part 3: add a free helper account (repeat for each one)
1. On the hub page: **Add account**, type a name (like *Helper1*), choose **free**, **Save**.
2. Press **Connect** and copy the link.
3. On claude.ai or the Claude phone app, signed in as that account: **Settings** › **Connectors** › **Add custom connector**. Name it *Dop hub*, paste the link, tick **No sign-in** (claude.ai marks it Detected; leave any OAuth client choice alone) and press **Add**; if a **Connect** button appears, press it (no sign-in page should open). **Test link** on the Connect screen checks the link first; **New link** makes a fresh one (connectors and routines using the old link stop working until you add the new one). Add stays grey while "Sign in now" with "Use your own OAuth client" is picked (it wants a client ID), until Name and URL both have text, or if that account already has a connector with the same link (**New link** fixes that). Use the link from the hub's main address (Vercel › Domains); single-deployment links are locked behind a Vercel login and fail with a sign-in error.

To put a helper to work, open a chat on it and type: **check the Dop hub**. It does one task, then asks the hub for the next.

## Using it
- **Storytime studio** (button under New task, or `/studio.html`): hand-drawn story animations made by a director + critic team; see `studio.md`.
- Type a task in **Project chat**. The coordinator opens threads and says where each went, with a card per thread. It splits every prompt into its independent tasks, one thread each (up to 8), so agents work in parallel; a single task, or parts that depend on each other, stays one thread.
- The buttons under the box pick, for that task: **Model** (Auto lets the coordinator choose), **Thinking** (Claude's own levels: Low, Medium, High, xHigh, Max), **Accounts** (any, or tick one or more; only those accounts work on it) and **Solo / Team of 2-4** (how many accounts work one thread together). **One thread** skips the coordinator. The picks are remembered on that device.
- **New chat** (top of the thread list, next to New task) opens a clean chat. What you send goes straight to one agent as a new thread: no coordinator runs and nothing is added to Project chat. It uses the same Model, Thinking, Accounts and Team picks.
- Tasks that need code go to paid accounts and start within seconds. Tasks that don't need code wait for a free helper; open a chat on it and type **check the Dop hub**.
- In a thread you can reply, change its **Model**, **Thinking** or **Accounts**, or press **Mark done**. The **⋯** menu archives a thread (hidden under **Archived** at the bottom of the list, no new sessions, can be restored) or deletes it with its messages.
- **Accounts stay connected**: a storage hiccup or a failed routine start no longer drops an account; the hub retries by itself and a low account comes back at its reset (or after 5 hours if the reset is unknown). A card that says **Needs you** tells you the one thing to fix. To have accounts back within a minute of a reset even with every page closed (optional, free), follow step 1 of [hub-setup-steps.md](hub-setup-steps.md) (add Upstash QStash to dop-hub, check `QSTASH_TOKEN` is set, Redeploy). Settings › "After a usage limit resets" says whether it is on. The same file says what to do when a card shows **Needs you**.
- **Team lessons** (second row in the thread list): when an agent learns a do or a don't, it saves it there. Every other agent gets it on its next hub call, and every new session starts with all of them. You can add your own there (they win if two disagree) and delete wrong ones.
- **Files in chat**: the **+** at the left under the box adds files (on a phone also photos); you can also drop them on the box or paste a screenshot. They upload to the Library at once (same limits: 24 MB a file, 10 a message) and show as chips; Send waits for them. A file can go without text. Project chat: every thread the coordinator opens from that prompt gets the files; New chat or a reply: that thread gets them, and the working agent is told each file's id to read with `lib_get` (in hub_wait, hub_read and its next handover reply). Tap a chip on a message to see or download it. Code: the "files in the chat box" part of `hub/index.html`, `chatFiles` / `attachFiles` in `hub/lib/library.js`; tests `tests/hub-attach.test.ts`.
- **Copy**: every prompt and reply has a **Copy** button (under your own messages, next to the time on the others); it copies that message's text.
- **Delete a message**: on a phone, swipe a message left and tap **Delete** (swipe right or tap elsewhere to keep it). On a computer, point at a message and click its **⋯**, then **Delete**. Only that message goes, on every device (they drop it at their next refresh). Deleting a coordinator reply does not make it route the prompt again.
- Each account card says **✓ Connected** once its connector link has been used with the right key, or **Not connected yet**.
- The **Team** panel shows each account's 5-hour and weekly limits (% used and when each resets), sorted with the freest first. When an account has less than the **minimum usage left** (Settings, default 15%, so 85% used) of either limit, the hub marks it low and moves new work elsewhere; its threads continue from their last handover. The coordinator sees each account's % left, and among equally busy accounts the one with the most left goes first. **Usage** on a card lets you type the numbers in or mark it **Running low** by hand.
- **Removing an account** (Edit › Remove): it disappears from every device at their next refresh, from the Accounts picker (and the picks saved on each device), from threads' account picks, from routing and from Settings › Coordinator account. The hub keeps a tombstone (`hub:accounts-gone`) so a usage read or routine start still in flight can't bring it back; adding the same name again clears it. A session it is already running keeps going until its next hub call is refused, then the stall check moves the thread on. Its old messages keep its name.
- **Activity per account**: each Team card shows what that account is doing now: its working threads (#id, title, lead or member, its last post and how long ago), its running sub-agents with progress, or "Idle · seen … ago".
- **Thinking**: while an agent works, its thread shows Claude Code's own thinking line (the ✻ spinner, a verb like *Pondering…* and the time so far) for each account on it, and Project chat shows one for the coordinator until it answers. Agents may post a short `thinking` note at key decisions. **✻ Thinking** at the top of a thread shows them folded (default), open or hidden, and per account. Other agents never receive these notes, so they cost the hub nothing. An agent's full private reasoning stays in its session (**Open session**).
- **Look** (Team panel footer, next to Settings): Theme **Auto** (follows the device), **Light** or **Dark**, and a background behind the whole page: Plain, Dots, Grid, Go board (wood grain), Stones (real-looking Go stones), Dawn (hills at sunrise; dusk in dark), Sea (sun on the water; moonlight in dark), Forest (misty pines) or Night sky (stars and the Milky Way, always dark). Text over a picture sits on frosted glass. Saved on that device only. The pictures are SVGs drawn by `node hub/walls.mjs`, which writes them into `hub/index.html`; edit that script, not the CSS between the `walls:` markers.
- **Logo**: a black stone and its white copy on a board (`hub/logo.svg`). It is the tab icon, and `hub/apple-touch-icon.png` is the icon for Add to Home Screen.
- **Sidebars close** (desktop): the panel icon at the top of each sidebar folds it away; the same icon in the chat header brings it back. Keys `[` (threads) and `]` (team) do the same when not typing. Saved on that device (`hub-panels`). Phones keep the Threads/Chat/Team tabs.
- **Tasks** (under the account cards, like a project's task list in Claude): every thread grouped as **Working on**, **Not started** and **Finished**, with counts. Tap one to open it.
- **Clawd**, Claude Code's mascot, redrawn from its terminal sprite (the same pixels and colour), sits by the hub name and scuttles while any thread is working. It also waves on the sign-in page and walks across an empty Project chat.
- **Team threads**: with Team of 2-4 (or when the coordinator picks a team for a big task), the hub starts a lead and members on different accounts, all with enough usage left, in one thread. The lead posts a plan (one part and branch per member), members wait for it, then each works its part. Every post reaches the whole team; `hub_post` with `to` addresses one teammate. Each member keeps its own handover; a member quiet for 15 minutes is replaced on another account from its handover while the lead carries on. A member's **done** closes only its part; the lead merges, opens the PR and closes the thread. If fewer accounts are free than asked, the thread says so and goes on with fewer. Each member is one more session, so it costs usage on that account.
- **Shared skills and questions**: `skill_list`, `skill_get`, `skill_put` give every account the same skills (`hub/lib/tools-skills.js`). The bundled set is a copy of `.claude/account-skills`, baked into `hub/lib/skills-seed.js` by `node hub/seed-skills.mjs` (run it after editing a skill there); `skill_put` saves a change for all accounts in the store. Gotcha: a saved copy wins over the bundled one, so after editing a skill in the repo either `skill_put` it again or Delete the saved copy in Library › Skills (the six ambition skills were saved live on 2026-10-22, identical to the bundled text). The agent rules say: a skill command (like `/clarify`) means skill_list, skill_get, then follow it. `ask_user` is the hub's AskUserQuestion: 1-4 multiple-choice questions show as tappable cards in the thread (answer text goes back to the agent as a reply); where a skill names AskUserQuestion and the agent has none, it uses `ask_user`.
- **Library** (button under New task, or `/library.html`): XIAO's own files, linked repos and skills, in three tabs; every agent on every account can read them. Nothing to set up: it uses the same Upstash store.
  - **Files**: pick, drop or (phone) choose from the camera roll. Any file up to 24 MB; the library holds 120 MB in all (under half the free 256 MB). Give each a note and tags: `studio` (Storytime reference), `do` (an example to follow), `dont` (what NOT to do); attach it to threads so those agents see it first. In the browser a big picture also gets a small copy (≤1568 px). A video gets measured in the browser, free and keyless (`hub/library/video-scan.js`): a scan of up to 300 tiny grey samples finds cuts and motion, up to 48 stills are picked at both sides of every cut, the middle of each shot, then an even spread, and go on contact sheets of 12 labelled `#n time` and "new shot"; the sound is decoded for loudness every 50 ms, hits and a steady beat (60-180 BPM). That timeline is stored as text and shown with the sheets. A video over 24 MB keeps only its stills and timeline. Tested on a real 6 s and 30 s VP9 clip in headless Chromium: both cuts and the 120 BPM click found exactly, 30 s took 6.6 s to prepare; not yet on a phone. Uploads go in 900,000-character pieces (Vercel takes 4.5 MB a request); one left unfinished for an hour is dropped.
  - Agents: `lib_list` (filter by tag, thread, kind, words) and `lib_get` (a picture comes back as an image; a video as all its sheets plus the measured timeline and Gemini's saved notes, `frame: n` for one still, `sheet: n`, `from`/`to` seconds for up to 8 stills in a span; text as text). **`lib_watch`** (`hub/lib/watch.js`): Gemini watches a kept video, or a public YouTube `url`, WITH sound and writes a timed breakdown (shots, easing, on-screen text, colour, music and what lands on it, a web rebuild timeline). It samples 1-10 frames a second (~180 in all; Gemini's default 1/s misses fast intros), gets the measured timeline in its prompt, sends ≤14 MB inline and bigger files through the Files API. The default breakdown is saved, so one Gemini call per video ever; `ask` is a new unsaved call, `fresh: true` redoes it. Needs `GEMINI_API_KEY` (or `LLM_API_KEY`) on the hub's Vercel project; optional `HUB_VIDEO_MODEL`. Free tier: Google may use what is sent to improve its models, so only reference clips. Tests `tests/hub-video.test.ts` (Gemini mocked; not yet run against the live API). Every agent's start text has a one-line summary of the library, the files attached to its thread and the linked repos; the Storytime brief tells the director and critic to look at `studio` refs before the first sample. `file_get` now also returns pictures as images. Code: `hub/lib/library.js`, `hub/library.html`, `hub/library/files.js`. Tests: `tests/hub-library.test.ts`, `tests/hub-library-files.test.ts`. Not verified on a real phone yet: Chromium here can't decode H.264, so an .mp4 from an iPhone was tested only in a mock; if frames fail, the video is still kept and the page says agents get the file only.
  - **Repos**: paste `owner/name` or any github.com link (a `/tree/<branch>` link sets the branch), add a note and threads. Agents get `repo_list` and `repo_read` (a folder, a file as text, a picture as an image, or `tree: true` for every path), from any account or chat, through the hub. Public repos need nothing. Cloud coding sessions clone one with their own `add_repo` tool (the start text says so). **Optional, only for private repos in chats**: in Vercel › the hub project › Settings › Environment Variables add `GITHUB_TOKEN` (a GitHub fine-grained token with read-only Contents access to those repos), then Redeploy; it also lifts GitHub's limit of 60 calls an hour. A repo the hub can't read is still listed, marked "hub can't read it" with GitHub's reason. Code: `hub/lib/tools-repos.js`, `hub/library/repos.js`; tests `tests/hub-repos.test.ts`.
  - **Skills** (tab): the shared skills (bundled and saved) to read, edit, create (New skill), or upload a SKILL.md; Delete removes a saved one and a bundled one reverts to its bundled text. Agents see changes at once through `skill_list` / `skill_get`.
- **Sub-agents and progress**: every account's session may deploy its own sub-agents (its Agent tool), not only ask other accounts. It reports each with `hub_agent` (start / update with step and 0-100 progress / finish done or failed, no model call). The state has `agents` (newest 60); the Team panel shows them live per account (title, step, progress bar, elapsed; "quiet" after 30 min without an update). Code: `agentRun` in `hub/lib/hub.js`.
- **Tools for agents (free, no keys)**: besides the hub tools, every connected Claude gets `web_fetch` (read any public URL as text; private/local addresses and redirects into them are blocked), `web_search` (DuckDuckGo's HTML results, Wikipedia's search as fallback) and `image_gen` (Pollinations, returns the picture; with the optional server env var `POLLINATIONS_API_KEY` set in Vercel it uses gen.pollinations.ai with the key as a Bearer header and the watermark goes away, without it the keyless endpoint stamps a watermark; with `thread: <id>` it also saves the picture under `images/` in the caller's file space and posts it into that thread, where the page draws it inline via `op=image`, max ~380 KB). Code: `hub/lib/tools-web.js`. Files: `file_put`, `file_get`, `file_list`, `file_delete` keep small files (512 KB each, 8 MB per account, 64 MB in all) in the hub's Upstash store so accounts share notes, logs, SGFs (`hub/lib/tools-files.js`); an account writes only its own files, anyone reads any. Nothing to set up: they run inside the existing function, so redeploy by merging. They call outside sites from Vercel, not from the Claude session, so cloud sessions with a locked-down network can still use them. Not verified live from the build sandbox (its proxy blocks those hosts): tested with mocked fetch only, so try each once after deploy. **No video generation**: no free, keyless video API is reliable enough to ship; `video_gen` is not added. If you later get a free key for one (for example a Hugging Face token), say so and it goes in as a new tool.

## Details (only if you need them)
- **How starting works**: a routine is a saved cloud task on one account with one model. The hub starts it through Claude's routine trigger (at most 30 times an hour per routine, 100 an hour per account). Each session reads its thread from the hub and works on the repo. Routines are marked experimental by Anthropic.
- **Why free helpers wait for you**: free plans can't run Claude Code or routines, so the hub can't start them. They only work when a chat is open, and they never get coding work.
- **Skills**: skills saved on an account load by themselves in that account's chats and cloud sessions; the repo's `.claude/skills` load in every cloud session. Each account needs its own copies (see `.claude/account-skills/`). The start message's rules tell agents to use the fitting `dop-*` repo skill.
- **How agents talk**: accounts can't reach each other directly, only through the hub, and the hub can't speak into a session that is busy. So every hub reply also carries what is new for that agent (replies in its thread, questions for it, answers to questions it asked, new lessons), and agents call `hub_sync` between steps. An agent waiting with `hub_wait`, `hub_ask` or `hub_post` with `wait_s` hears a new message in 0.8 s on average and 1.2 s at worst (scratch benchmark, 20 runs, 80 ms per store trip; 0.9 s and 1.7 s with the 1.5 s check before). A busy agent hears it at its next step. Subagents inside one session are still faster, since they share the session.
- **Lessons**: agents save them with `hub_learn` (one sentence, do or don't, and why). The hub keeps 100; when full, the oldest one an agent wrote makes room (yours stay). Text that looks like a key or token is refused, because lessons go to every account. Workers get all lessons in their start brief (about 40 tokens each, counted in the hub's overhead); the coordinator only gets yours.
- **Handover**: agents save what's done, the exact next step and the branch after each milestone. If a working thread goes quiet for 15 minutes, the hub restarts it on another account from that handover (at most once every 30 minutes per thread; it can be turned off in Settings).
- **Usage** (measured 2026-10-20): one coordinator run on Haiku took 4 turns, 3 to 15k new tokens plus about 180k cached reads, about US$0.004 at API prices. The hub's own messages are about 500 tokens per prompt. The page shows the hub's overhead for the last 5 hours against a budget (default 60k tokens, set in Settings); over budget, prompts skip the coordinator. Anthropic doesn't publish the free plan's 5-hour limit as a number, so staying under half of it can't be proven.
- **Thinking level**: routines have no effort setting the hub can change, so the level goes in as words Claude Code reads at the top of the start message: Medium "think", High "think hard", xHigh "think harder", Max "ultrathink", plus a line in the brief. Not measured yet whether this changes how long the sessions think.
- **Where usage numbers come from** (checked 2026-10-21, thread #357):
  - **Agents (automatic, main source).** Every hub agent runs `node hub/usage-probe.mjs` when it starts and again when a `hub_checkpoint` reply says usage is due (last reading over 30 minutes old), then sends the numbers with `hub_usage`. The script makes one tiny Haiku call through the session's own `claude` CLI (`-p`, stream-json, no tools, no repo context: about 1.4k tokens, US$0.0003 at API prices, 2 s). Claude Code then prints a `rate_limit_event` holding the account's 5-hour and weekly use and reset times, the same numbers as claude.ai › Settings › Usage. Measured on ME 2: 5h 15%, week 62%. The card says "reported by its agent". Claude Code only prints the event for Pro and Max logins, so free accounts still need the numbers typed in. The script never reads a token.
  - **What the hub can't fetch by itself.** Routine tokens are documented as "scoped to triggering that task only", so `api/oauth/usage` refuses them (401/403). The hub now asks again only every 6 hours after a refusal. The fire response carries no usage either. So an account that runs no agent keeps its last reading: the 5-hour number for 5 hours, the weekly one (with its age) until its weekly reset. Fresh numbers need an agent session on it, the PC status line (`hub/pc-statusline.mjs`, every 10 min), or typing them in.
  - **Live activity.** Every hub call from an agent updates the account's "last seen", and its threads and sub-agents show on the Team card. Nothing reaches the hub between calls.
- **Continuing after a usage limit resets** (2026-10-21, sharper 2026-10-22): when every account is at its limit, a thread waits (`queued`, `wait: 'usage'`) or stays `stalled`. The hub's wake check (`wake` in `hub/lib/hub.js`) drops a limit's number once its reset time passes, clears the low mark (the card shows "back HH:MM"), posts "Usage limit reset: …", then restarts up to 8 waiting threads from their handover and starts the coordinator for a prompt nobody routed. It runs at most once a minute, from: any agent's hub call and any open page poll (`wakeIfDue`, remembered per server instance so most calls skip it); the **timed wake** (`hub/lib/wake-timer.js`: with `QSTASH_TOKEN` set, the hub asks Upstash QStash to post `{op:'tick', due}` to `/api/hub` 15 s after the next known reset or retry time; that tick runs even right after another check, at most every 10 s); and the **Hub wake** workflow (`.github/workflows/hub-wake.yml`, asked for every 10 min, but GitHub ran it only every 2.5 to 5 hours on 2026-10-21/22, so it is a backstop). When it is low: from usage numbers → back when they drop (their reset, or the reading's age); agent's `hub_usage("low")` → its reset (also a bare `*_resets` time), else 5 hours; XIAO's **Running low** → its known reset, else 5 hours. A session the hub started that never reaches the hub, while nothing else from that account does either, means it is out of usage or its connector is broken: that account rests 1, 2, 4, then 5 hours. Free accounts can't be started by the hub, so their chat-only work goes to a paid routine or waits for "check the hub". Tests: `tests/hub-wake.test.ts`, `tests/hub-connect.test.ts`.
- **Staying connected** (2026-10-22): Upstash calls that fail with busy or gateway errors are tried twice more (reads also after a lost connection; writes never twice), and an MCP request whose storage read still fails answers 503 so claude.ai keeps the connector. A failed routine start pauses that routine and the hub retries it by itself: no answer twice (one quick second try first) → 2 min; 429 → Claude's Retry-After, else 10 min; 401/403 or another 4xx → 30 min, and the card says **Needs you** with the fix (copy the routine's id and token again), announced once in Project chat. A connector calling with an old key (after New link) shows **Needs you** with a **Reconnect** button until a good call arrives. Paused accounts show **Paused** with the retry time.
- **Saving usage**: turn on **One thread** under the box for simple tasks.
- **PC agents (optional)**: `claude mcp add --transport http dop-hub "<link>"`. Set `HUB_MCP_URL` to the link and use `hub/pc-statusline.mjs` as the status line to report low usage automatically.
- **Speed**: one page refresh is one store round trip (measured with 80 ms per trip: 82 ms, was 1,535 ms and 25 trips), the page only fetches messages it doesn't have, opens from its last view on reload, and shows your message before the hub answers. Settings › Speed shows the last refresh time. Agent calls batch their store work (Lua scripts for posting, news and the page snapshot; writes like the connection log and news markers ride on the call's last trip; the stopped-agent check is skipped until a thread could be stale). Scratch benchmark, 80 ms per trip: hub_post 15 → 5 trips (1.2 s → 0.4 s), hub_sync 8 → 4 (0.57 → 0.24 s), hub_checkpoint 14 → 5, hub_read 8 → 4-5, a changed page poll 2 trips/13 commands → 1/1.
- **Fewer calls (agents)**: `hub_post` takes `wait_s` (max 45) and returns teammates' replies in the same call, so a post-then-wait is one tool call. `hub_post` with `wait_s`, `hub_wait` and `hub_ask` poll with one cheap counter read every second and only read new messages when the counter moved (was a full 400-message read every 3 s).
- **Storage**: the page checks for news every 3 seconds while it's open. Waiting agents check every second with one small read (an idle 20-second wait uses about 30 of Upstash's free 500,000 monthly commands and reads 1 KB).
- **Other projects / own repo**: `HUB_PROJECT` and `HUB_OWNER` (Vercel env vars) rename the hub for another project; moving its code to its own repo is in `hub-split.md`.
- **PC-only version**: `tools/hub/` (see `hub.md`) still works offline.
- Code: `hub/`. Tests: `tests/hub-cloud.test.ts`.

## Vercel deployment limit (2026-10-21)
- Symptom: a PR check says deployments are limited and resets in 24 hours. Cause: Vercel Hobby allows about 100 deployments a day, and three projects (Dop, Kami, hub) build from this one repo, so each push counted up to three times. Bot data commits (AI training, coach training, problem bank) and parallel threads pushing after every edit used it up.
- Fix: each `vercel.json` has an `ignoreCommand` that skips the build when a push changes nothing that project uses. Dop skips docs, `.claude`, `.github`, `hub`, `eval`, `data`, scripts and tests. Kami also skips the bot data folders under `public/` (student, book, level, coach, problems, broadcast). The hub builds only when `hub/` changes. The commands compare the last commit with the one before it, and build if that comparison fails, so a doubt always builds.
- Vercel rejects an `ignoreCommand` over 256 characters before building ("schema validation failed"). Dop uses short `:!path` excludes; Kiai keeps its list in `kami/vercel-ignore.sh` (`sh vercel-ignore.sh`). Add new exclusions there, not in vercel.json.
- Dop still builds on bot data commits, because that data is served by the site.
- Gotcha: a skipped build shows as canceled or ignored on the PR, which is expected. A docs-only commit never redeploys production; the next code push does.
- Threads push once, when done (CLAUDE.md and dop-ship-pr).


## Page code map (hub UI pass, 2026-10-22, PRs #102-#113)
- Look: default is "Kaya" (honey sidebar and headers, cream middle, black-stone main buttons, white stones in dark, Alegreya Sans self-hosted in `hub/fonts`, 6 px radius, 2 px bottom edge on pressable things). Tokens and one marked component block sit at the top of each page's CSS; change colours there. With a Look › Background picture the sidebar goes back to frosted glass. The studio still loads Patrick Hand because `studio/render.js` draws captions in it.
- Icons: `hub/ui/icons.js` is the only source (Lucide, ISC, some Feather-derived MIT; both texts in `hub/THIRD_PARTY_NOTICES.md`). Add a path to `P`, then `icon('name', size)` in JS or `<i data-ico="name" data-size="16">` in HTML. `dev.mjs` serves `/ui/*.js`; Vercel serves it with no config.
- Feed: agent text goes through `hub/ui/md.js` (escape first, then mini markdown, http(s) links only; tests in `tests/hub-md.test.ts`). The feed is patched by item key (`patchFeed`) and `msgHtml` output is cached per message in `msgItem`: if `msgHtml` reads new outside state, add it to `feedCtx()` or the memo key. A thread draws its newest 100 messages; "Show earlier messages" adds 100 (`feedEarly`).
- Polling: the page asks `op=state&v=<seq>&since=<id>&tu=<updatedAt>`; an unchanged poll is 1 Upstash command. Pace 3 s → 6 s → 10 s (work running) / 30 s (none), paused while hidden, refreshed on focus. Every thread write must go through `putThread` (sets `updatedAt`) or open pages miss it. The 5-min usage read (~32 commands) is now the biggest per-tab cost.
- Compose and sheets: only changed picks show as chips; the Options popup (`openPop('opts')`) holds all of them. Drafts in localStorage `hub-drafts`, send state in `sendSt[sel]`. Sheets use `sHead()` / `sFoot()` / `fld()` / `fieldErr()`.
- Threads and team: rows are one line (`.trow.t1`); the filter box `#tFind` shows from 8 threads. Amber means only "Needs you". Team cards keep rare actions in a ⋯ menu (`openPop('amenu:<name>')`, `acctMenu`).
- Phone: sizing, safe-area and keyboard rules are in the `@media (max-width: 860px)` block and the `visualViewport` listener (`html.kb` while the keyboard is open). `hub/manifest.webmanifest` is the home-screen manifest.
- Library: files carry a small `thumb` piece (`hasThumb`, made at upload or once via `lib-thumb`), cached in the Cache API. Page op `skill-list` has no texts; `skill-get&name=` reads one. Tabs refetch on switch or focus only after 30 s.
- Studio page: tabs are keyboard-navigable (`openTab`); `drawCast()` runs only while the Cast tab is open.
- Caching: `hub/vercel.json` caches js/mjs/svg/png/woff2 for 5 min with stale-while-revalidate (files are not hashed); html is `no-cache`.
- Class names already taken: `.wide` (hidden on phones), `.fill` (usage bars), `.more` (header ⋯). Pick new names for new parts.
